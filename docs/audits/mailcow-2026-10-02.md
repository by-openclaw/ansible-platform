**Incident log (same day; every cause closed in the role):**
- 14:29–14:40Z — the first `update.sh` run on the shallow, tag-detached checkout stopped the stack and died (`fatal: No current branch`); `--skip-start` left mail down 9 min (restored with `--tags compose`). Fix: full clone on branch `master`, an older checkout converted in place (a clone made at a tag only ever fetched that tag — refspec restored, unshallowed).
- 15:00–15:12Z, 16:01–16:06Z, 16:15–16:36Z — after a network recreate (`ENABLE_IPV6` flip: `update.sh` forces `false` whenever its external IPv6 ping fails — no override in `ipv6_controller.sh` — and the role renders `true`), Compose re-attached the running containers with dynamic addresses: `unbound-mailcow` lost `.254`, internal DNS dead → web and dockerapi down, SMTP up (deliveries deferred, not lost). Fix: the update runs only while the nearest tag differs from the pin (`git describe` reports `2026-09-3-g…` once master carries hotfixes, so the exact compare re-ran `update.sh` on every apply), and a changed network definition stops the stack first so the compose step recreates every container with its static address. The last window was two of my runs overlapping on the host (a replacement chain started while the previous one still had an apply ahead of it).

Found on the way: `roles/cloudflare_dns` CAA passthrough; Cloudflare adds its partner CAs to a Universal-SSL zone as soon as any CAA record exists (expected). Until the DMZ host has IPv6 egress, every vendor update costs one extra stack recreate (~2 min) to restore `ENABLE_IPV6=true`.

## Owner decisions applied after the closure

- **2026-10-03 — the mail VM moved in place from Debian 12 to Debian 13.7** (`playbooks/os-release-upgrade.yml`, hypervisor snapshot first; Docker CE 29.8.2). The record had not flagged the Debian 12 host (found while refreshing the status page).
- **Incident during that upgrade (mail down ≈30 min, 21:48–22:19Z):** the release upgrade installed `exim4` (a Recommends: this host carries no MTA of its own), which bound `127.0.0.1:25` and `[::1]:25`; Docker could not publish the Postfix container's port and the container stayed `Exited (128)`. Fix in the role: `mailcow_host_mta_absent` keeps the exim4 packages absent and a check fails the play when anything but Docker holds port 25. After the removal the Postfix container showed `Up` but **without a network** (Docker leaves a container detached when publishing its port failed once; Compose sees no change): recreated, it got its address and ports back and the SMTP probes turned green at 22:19Z — mail was down ≈30 min in total. `roles/compose_stack` now detects a running container without a network attachment and recreates it.
